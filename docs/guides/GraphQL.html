What is GraphQL, really?

fundamentals

GraphQL is a query language for your API + a runtime that fulfills those queries. You describe what data exists; the client asks for the shape it wants; the server returns exactly that shape — nothing more, nothing less.

✗ REST: over/under-fetching

To show a user's name + their 3 recent posts, you'd hit GET /users/1 then GET /users/1/posts. You probably got the user's email, address, and 50 posts you didn't need.

✓ GraphQL: one round-trip

One request, exactly the fields you want, nested as deep as the schema allows. The server resolves each field in parallel and returns a JSON shape that mirrors your query.

Junior takeaway: REST endpoints = verbs (URLs). GraphQL = nouns (types) + you choose the verbs. The frontend becomes the architect of its own data.

The four pillars

mental model

Q Query

Read data. Like a GET. You describe the shape; you get JSON back in the same shape.

M Mutation

Write data. Like POST/PUT/DELETE. Always returns data too — what changed.

S Subscription

Real-time push over WebSocket. Server emits when data changes. Great for live updates.

T Type System

The schema. Every field has a type, every type has fields. This is the contract.

Senior insight: The schema is the single source of truth. Backend devs, frontend devs, tooling, mocks, tests — all read from it. Lose the schema, lose everything.

The schema — your contract

SDL

Written in Schema Definition Language (SDL). Every type, field, and relationship lives here. Here's a small blog schema we'll reuse throughout:

schema.graphql
# The root query type — every read starts here
type Query {
  me: User!
  user(id: ID!): User
  posts(limit: Int = 10, offset: Int = 0): [Post]!
}

type Mutation {
  createPost(input: CreatePostInput!): Post!
}

type User {
  id: ID!
  name: String!
  email: String
  posts: [Post]!
}

type Post {
  id: ID!
  title: String!
  body: String!
  author: User!
  createdAt: DateTime!
}

input CreatePostInput {
  title: String!
  body: String!
}
The ! matters. User = nullable. User! = guaranteed non-null. [Post] = list may be null AND items may be null. [Post!]! = always a list, always non-null items. Get these right; they're your runtime safety net.

Setting up Apollo Client

setup

Apollo Client is the most mature GraphQL client for React. It gives you caching, loading/error states, refetching, and devtools out of the box.

Install dependencies

terminal
# Apollo Client + GraphQL core
npm install @apollo/client graphql

# (Optional, recommended) typed document nodes
npm install -D @graphql-codegen/cli @graphql-codegen/client-preset

Create the client

src/lib/apollo.ts
import { ApolloClient, InMemoryCache, HttpLink } from '@apollo/client';

export const apolloClient = new ApolloClient({
  link: new HttpLink({
    uri: 'https://api.example.com/graphql',
    // Attach auth token from localStorage on every request
    headers: () => ({
      Authorization: `Bearer ${localStorage.getItem('token') ?? ''}`,
    }),
  }),
  cache: new InMemoryCache({
    // Tell Apollo how to identify objects by type
    typePolicies: {
      Post: { keyFields: ['id'] },
      User: { keyFields: ['id'] },
    },
  }),
});

Wrap your app

src/main.tsx
import { ApolloProvider } from '@apollo/client/react';
import { apolloClient } from './lib/apollo';
import App from './App';

ReactDOM.createRoot(document.getElementById('root')!).render(
  <ApolloProvider client={apolloClient}>
    <App />
  </ApolloProvider>
);

Running queries in React

useQuery

The useQuery hook is your bread and butter. It gives you loading, error, and data. Apollo also caches the result — if two components ask for the same data, it's served from cache.

src/features/posts/PostList.tsx
import { useQuery, gql } from '@apollo/client';

// 1. Define the query as a typed document
const GET_POSTS = gql`
  query GetPosts($limit: Int) {
    posts(limit: $limit) {
      id
      title
      author {
        name
      }
    }
  }
`;

export function PostList() {
  // 2. Run the query
  const { loading, error, data } = useQuery(GET_POSTS, {
    variables: { limit: 10 },
    // Skip cache for fresh data on mount (optional)
    fetchPolicy: 'cache-first',
  });

  if (loading) return <Spinner />;
  if (error) return <ErrorBanner message={error.message} />;

  return (
    <ul>
      {data.posts.map(p => (
        <li key={p.id}>{p.title} — by {p.author.name}</li>
      ))}
    </ul>
  );
}
Wait — this isn't typed! data.posts[0].author.name is any. Apollo doesn't know the shape. We fix this in Section 08 — Codegen. This is the #1 thing separating junior from senior GraphQL codebases.

Mutations — write & sync cache

useMutation

Mutations change data. The tricky part isn't running them — it's keeping your cache consistent afterward. Three strategies, in order of preference:

1 Return what changed

Best: the mutation returns the full updated object. Apollo auto-merges by id + __typename. Zero manual work.

2 refetchQueries

Easy but expensive. Tell Apollo which queries to re-run after the mutation lands.

3 update() callback

Manual cache writes. Most control, most bugs. Use when the others can't express the change.

4 Optimistic UI

Update the cache before the server responds, rollback on error. Feels instant to users.

CreatePostForm.tsx
const CREATE_POST = gql`
  mutation CreatePost($input: CreatePostInput!) {
    createPost(input: $input) {
      id
      title
      body
      author { id name }
    }
  }
`;

function CreatePostForm() {
  const [createPost, { loading }] = useMutation(CREATE_POST, {
    // Strategy 2: refetch the list to include the new post
    refetchQueries: ['GetPosts'],

    // Strategy 4: optimistic response — show the post instantly
    optimisticResponse: ({ variables }) => ({
      __typename: 'Mutation',
      createPost: {
        __typename: 'Post',
        id: 'temp-' + Date.now(),
        title: variables.input.title,
        body: variables.input.body,
        author: { __typename: 'User', id: 'me', name: 'You' },
      },
    }),
  });

  return (
    <form onSubmit={e => {
      e.preventDefault();
      createPost({ variables: { input: { title, body } } });
    }}>
      {/* ...inputs... */}
      <button disabled={loading}>Publish</button>
    </form>
  );
}
Gotcha: refetchQueries uses the operation name, not the query string. If your query is query GetPosts, the name is 'GetPosts'. Mismatch = silent no-op.

Type safety with GraphQL Codegen

typescript

This is what makes GraphQL + TypeScript actually sing. Instead of any everywhere, codegen reads your schema + your .graphql files and generates fully-typed hooks. You never write a manual interface again.

Add the config

codegen.ts
import { CodegenConfig } from '@graphql-codegen/cli';

const config: CodegenConfig = {
  schema: 'https://api.example.com/graphql',
  documents: ['src/**/*.{ts,tsx,graphql}'],
  generates: {
    'src/gql/': {
      preset: 'client',
      plugins: [],
    },
  },
  ignoreDocuments: ['**/node_modules/**'],
};
export default config;

Add npm scripts & run

package.json
{
  "scripts": {
    "codegen": "graphql-codegen",
    "dev": "npm run codegen && vite"
  }
}

Use the generated hook

PostList.tsx — fully typed
import { graphql } from '../gql';

// graphql`` is a tagged template that generates a typed hook
const GetPostsDocument = graphql`
  query GetPosts($limit: Int) {
    posts(limit: $limit) {
      id
      title
      author { name }
    }
  }
`;

function PostList() {
  // useGetPosts is auto-generated by codegen
  const { data } = useGetPosts({ variables: { limit: 10 } });

  // data is fully typed: { posts: { id, title, author: { name } }[] }
  return data?.posts.map(p => <li key={p.id}>{p.title}</li>);
}
Why this is senior-tier: If the backend renames title to headline, your build breaks locally before merge. Type errors catch breaking changes at compile time — no more "works on my machine."

Senior patterns you should steal

production

① Colocate queries with components

Put the graphql tag in the same file as the component that uses it. Don't dump all queries in queries.ts. Easier to delete, easier to find.

② Fragments for reuse

Extract PostCardFields as a fragment. Compose it into multiple queries. Change once, update everywhere.

③ Typed error policies

Use errorPolicy: 'all' when partial data is OK. The default 'none' throws away partial results.

④ Pagination with cursors

Use fetchMore + Relay-style cursor pagination. Avoid offset for mutable lists — items shift.

⑤ Persisted queries

Send a query hash instead of the full string. Smaller payloads, security benefits. Apollo Server supports this natively.

⑥ Schema-first > code-first

Design the schema as a team before writing resolvers. It's the API contract — get it reviewed like one.

Fragments example
// Define once
export const PostCardFields = graphql`
  fragment PostCardFields on Post {
    id
    title
    author { name }
    createdAt
  }
`;

// Reuse everywhere
const GetFeed = graphql`
  query GetFeed {
    posts(limit: 20) {
      ...PostCardFields
    }
  }
`;

Pitfalls that bite juniors

warnings

✗ N+1 queries via the client

Don't render a list, then fire a query per item. Use one query with nested fields. The whole point of GraphQL is one request.

✓ One query, nested data

posts { author { name } } — done. The server resolves the join; you get one payload.

✗ Returning huge unbounded lists

posts with no limit argument → return 100k rows → server dies. Always paginate.

✓ Pagination is mandatory

Force first/after (Relay) or limit/offset in the schema. Reject unbounded queries in resolvers.

✗ Trusting client input

GraphQL doesn't validate business rules. Validate inputs in resolvers; use custom scalar types (e.g. Email, URL).

✓ Validate + authorize at resolver layer

Use @auth directives or middleware. Never assume the client won't ask for fields they shouldn't see.

Deep nesting attacks: a malicious client can send posts { author { posts { author { posts { ... } } } } } and blow up your DB. Use query depth limiters (e.g. graphql-depth-limit) in production. Always.
