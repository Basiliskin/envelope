    🚩 Over-engineering radar

    Before adding any component, answer these three:

    1. What problem does it solve?If you can't name a current, real pain — wait.
    2. What does it cost?Ops burden, latency, consistency, debugging difficulty.
    3. What breaks without it?If the answer is "nothing today", it's a luxury, not a need.

    🎤 The 6-step interview playbook

    Use this exact order in the room. It keeps you from jumping to tools too fast.

    1. Clarify requirements. Functional + non-functional. Ask about scale: users, QPS, data size, read/write ratio.
    2. Estimate. Back-of-envelope: storage per year, requests/sec, cache size. Numbers justify architecture.
    3. High-level design. Client → LB → services → DB, with cache and queue where needed. Draw before deep-diving.
    4. Data model & APIs. Sketch schemas and 2–3 endpoint contracts. SQL vs NoSQL choice with reasons.
    5. Scale the bottlenecks. Reads → index, cache, replicas. Writes → async queues, batching. Only last: sharding.
    6. Reliability & ops. Failure modes, idempotency, DLQs, monitoring, rollouts. End with trade-offs you accept.
    💬 Trade-offs > tools. Always say what you give up when you pick something.
    🧱 Start boring. Monolith, one DB, one cache, one queue. Scale only when forced.
    🙋 Call out red flags yourself. "I would NOT shard here because…" scores points.
    🔢 Estimate first. "10 GB fits one Postgres easily, so no sharding" beats hand-waving.
