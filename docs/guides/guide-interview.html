The Event Loop, Practically

CORE

Concept: Node processes I/O in phases on one thread; microtasks drain between phases. Your handler must yield quickly or every request suffers.

Real-world: An ingest service p99 jumped from 12ms to 900ms — a teammate added a synchronous 8MB JSON.parse per batch. One line, all tenants affected.

Best practices: Budget ≤5–10ms per handler tick; stream big payloads; monitor loop lag; offload CPU work.

DO
  • Chunk big parses/loops
  • Use monitorEventLoopDelay alerts
DON'T
  • Sync fs/crypto on hot paths
  • Unbounded fan-out

Pitfalls: Believing await = parallelism; forgetting microtasks starve timers.

Quiz: A Promise.resolve().then() callback vs setTimeout(fn, 0) — which runs first, and why?
The promise callback — microtasks drain before the timers phase runs, even for a 0ms timer scheduled earlier.

Backpressure

CORE

Concept: Slowing a producer when consumers can't keep up — TCP flow control, Node stream pause/drain, gRPC flow-control windows, Kafka fetch limits.

Real-world: Gateways batching 50k readings/sec into an ingest that processes 30k. Without pushback, the ingest's in-memory queue grew until OOMKilled. With credit-based flow, gateways buffer locally and retry.

Best practices: Bounded queues everywhere with explicit overflow policy (reject / buffer-to-disk / shed load).

DO
  • Check write() return; await drain
  • Expose queue depth as a metric
DON'T
  • Let arrays grow without bound
  • Silently drop data when full

Pitfalls: Treating "Kafka buffers it" as a design; retry storms removing the pressure signal.

Quiz: Your Node stream's write() returns false. What do you do?
Stop writing and wait for the 'drain' event before resuming — otherwise you buffer unbounded in process memory.

Idempotency & "Exactly-Once"

ADVANCED

Concept: Retries are mandatory in distributed systems; duplicates are the price. Idempotent processing = same input applied N times yields the same state.

Real-world: A gateway retransmit after a timeout doubled every device's "alert fired" event. Fix: dedup key (device_id, seq) claimed with SET NX before side effects; replay returns stored result.

Best practices: Client-generated idempotency keys; atomic claim before action; persist results for replay; unique constraints in DB as backstop.

DO
  • Claim → act → store result
  • TTL the dedup window deliberately
DON'T
  • Check-then-act without atomicity
  • Trust "Kafka exactly-once" end-to-end

Pitfalls: Dedup window shorter than max retry interval; side effects before the claim.

Quiz: Why is "check if processed, then process" race-prone, and what's the fix?
Two retries can both pass the check concurrently. Fix: an atomic claim — SET NX / INSERT ... ON CONFLICT — where only one writer wins.

Retries, Backoff & Circuit Breakers

INTERMEDIATE

Concept: Retry transient failures with exponential backoff + jitter; open a circuit breaker when a dependency is down so you fail fast instead of piling on it.

Real-world: Inference service deploys caused 30s blips. Callers retrying instantly turned a blip into a brownout. Adding jitter + a breaker (open at 50% errors, half-open probe) made deploys invisible.

Best practices: Retry budgets per caller; jitter always; breakers on synchronous calls; never retry non-idempotent writes without a key.

DO
  • Cap total retry time < caller's deadline
  • Alert on breaker state changes
DON'T
  • Retry forever / fixed-interval storms
  • Breaker-wrap a Kafka consumer offset commit

Pitfalls: Retry amplification through 5 hops; no jitter = synchronized hammering.

Quiz: What does an OPEN circuit breaker do, and why is that good?
It short-circuits calls locally (fail fast) without touching the failing dependency, giving it recovery time; half-open probes test readiness.

Kafka Partitions & Consumer Groups

ADVANCED

Concept: Order + parallelism unit = partition. A consumer group divides partitions among members; one partition → one consumer per group; rebalance on membership change.

Real-world: Keying by tenant_id gave one whale tenant 40% of traffic on one partition. Re-keying to tenant+device hash spread load; per-device order still held.

Best practices: Choose the finest key that still needs ordering; size partitions for max parallelism; monitor lag per partition; sticky assignors to calm rebalances.

DO
  • Process → commit (at-least-once + dedup)
  • Plan partition growth before launch
DON'T
  • More consumers than partitions
  • Commit before processing "for speed"

Pitfalls: Hot partitions; rebalance storms during rolling deploys (mitigate with session timeouts + static membership).

Quiz: 12 partitions, 16 consumers in one group. What happens?
12 consume, 4 sit idle. Parallelism is capped by partitions — scale partitions first, or use the idle capacity for another group's work.

Multi-Tenant Isolation Patterns

ADVANCED

Concept: Spectrum from DB-per-tenant (max isolation, ops cost) → schema-per-tenant → shared rows + tenant_id with Row-Level Security (best density). Combine with per-tenant quotas everywhere.

Real-world: One tenant's report query table-scanned 400M rows and degraded everyone. Fixes: composite (tenant_id, ts) indexes, RLS fail-closed, statement timeouts, and read-replica routing for heavy tenants.

Best practices: Tenant in every index on shared tables; RLS as backstop; per-tenant rate limits + quotas; leak tests in CI.

DO
  • Propagate verified tenant context end-to-end
  • Noisy-neighbor detection alerts
DON'T
  • Trust client-sent tenant headers
  • Cross-tenant joins "just this once"

Pitfalls: Tenant as afterthought in caching keys, logs, and queues — leaks hide in the layers you forget.

Quiz: What does RLS buy you that application WHERE clauses don't?
Defense in depth: even a buggy or missing WHERE clause can't return another tenant's rows — the database enforces isolation per-session/context.

mTLS & Zero Trust Networking

ADVANCED

Concept: TLS proves the server; mTLS proves both sides. Workloads get cryptographic identity (certs, ideally short-lived/SPIFFE-style), so trust never comes from "it's inside the VPC."

Real-world: Gateways in customer data centers can't rely on network perimeter. Each gateway gets a provisioned cert; the cloud verifies identity and tenant binding before accepting a single reading.

Best practices: Automate issuance/rotation; deny-all network policy + explicit allows; tie cert identity to tenant/device registry.

DO
  • Short-lived certs + automated rotation
  • Log auth failures as security events
DON'T
  • Long-lived shared certs per environment
  • IP allowlists as identity

Pitfalls: Cert expiry outages (monitor!); hand-managed keystores; forgetting on-prem clocks skew cert validation.

Quiz: A gateway's cert is valid but it's sending data tagged for another tenant. Where do you stop it?
At ingestion authorization: the tenant claimed in payloads must match the tenant bound to the gateway's certificate identity in the device registry — authN passed, authZ still applies.

BFF — Backend for Frontend

INTERMEDIATE

Concept: A service shaped for one UI: aggregates multiple backends into screen-ready payloads, owns auth/session edges, fan-out caching, and live-update channels.

Real-world: A fleet dashboard needed 6 backend calls per page. The BFF collapsed them into one aggregated response (p95 2.4s → 380ms) and streams live deltas over WebSocket.

Best practices: Thin aggregation + caching + auth; domain rules stay in domain services; per-tenant rate limits at the BFF edge.

DO
  • Batch + parallelize upstream calls with timeouts
  • Cache aggregated views keyed by tenant
DON'T
  • Put business logic in the BFF
  • Let one UI's BFF become everyone's API

Pitfalls: God-BFF; duplicating validation; N+1 fan-out to services per render.

Quiz: Where does per-tenant rate limiting best live for browser traffic, and why?
At the BFF edge — it's the first authenticated, tenant-aware hop, so you protect every downstream service with one policy point.

Observability: RED, Lag & Traces

INTERMEDIATE

Concept: RED (Rate, Errors, Duration) per service; consumer lag and queue age for async paths; end-to-end trace IDs across tiers; logs with tenant + correlation IDs.

Real-world: "The dashboard is slow" became answerable in 60 seconds when a trace showed the BFF waiting on an inference projection 40 seconds stale — consumer lag was the real culprit.

Best practices: SLOs + burn-rate alerts; lag as a first-class SLO; synthetic probes from edge to cloud; dashboards per tenant for support.

DO
  • Propagate one trace/span context through Kafka headers
  • Alert on symptoms (SLO burn), not every cause
DON'T
  • Log payloads with tenant secrets/PII
  • Dashboards without on-call ownership

Pitfalls: Metrics without exemplars; alerts nobody acts on; per-tenant views missing when support calls.

Quiz: Requests are fast but users see stale data. Which async-path metric do you check first?
Consumer lag / projection freshness — synchronous p99 can be healthy while the pipeline feeding the view is minutes behind.

Five problems highly probable for a Node/TS platform lead. Practice writing them from scratch in 20–25 minutes each, narrating your reasoning.

Problem: Given N async task factories and a limit k, run at most k concurrently and return results in input order.

Step-by-step

  • 1. Allocate a results array sized to inputs (preserves order without sorting).
  • 2. Spawn min(k, N) worker loops; each grabs the next index atomically-ish (single-threaded JS: a shared counter is safe between awaits).
  • 3. Workers exit when indices run out; await all workers.
limitPool.js
// Run async task factories with at most `limit` in flight
async function limitPool(factories, limit) {
  const results = new Array(factories.length);
  let next = 0;
  async function worker() {
    while (next < factories.length) {
      const i = next++;
      results[i] = await factories[i]();
    }
  }
  const n = Math.min(limit, factories.length);
  await Promise.all(Array.from({ length: n }, worker));
  return results;
}

Complexity: O(N) time, O(N + k) space. Common mistakes: firing all tasks then "limiting" (damage already done); losing input order; forgetting k > N edge case; not deciding error semantics (fail-fast vs settle-all).

Follow-ups: Add per-task timeout. Add retry with backoff inside the pool (mention: retrying inside the pool still respects the limit). Per-result errors via Promise.allSettled semantics. How would this change across processes? (queue-based workers.)

  • 1. JS Map preserves insertion order — exploit it as the recency structure.
  • 2. On hit: validate TTL, delete + re-insert to move to most-recent.
  • 3. On insert at capacity: evict the first key (oldest).
lru.js
class LRUCache {
  constructor(cap, ttlMs) { this.cap = cap; this.ttl = ttlMs; this.map = new Map(); }

  get(k) {
    const e = this.map.get(k);
    if (!e) return undefined;
    if (this.ttl && Date.now() > e.exp) { this.map.delete(k); return undefined; }
    this.map.delete(k); this.map.set(k, e);  // refresh recency
    return e.v;
  }

  set(k, v) {
    if (this.map.has(k)) this.map.delete(k);
    else if (this.map.size >= this.cap)
      this.map.delete(this.map.keys().next().value); // evict LRU
    this.map.set(k, { v, exp: Date.now() + this.ttl });
  }
}

Complexity: O(1) get/set amortized; O(cap) space. Common mistakes: double-linked-list + hashmap implementation bugs (fine in Java interviews; in JS the Map-order trick shows platform fluency); lazy expiry only (mention periodic sweep for memory). Follow-ups: Make it distributed (Redis semantics, evictions under maxmemory). Cache stampede: add single-flight/locking. Sharding by tenant to avoid hot keys.

Problem: allow(key) returns true if the key made fewer than L requests in the last W ms.

Step-by-step

  • 1. Keep a queue of timestamps per key.
  • 2. On each call, drop timestamps outside the window, then compare count to limit.
  • 3. Note the Redis version (ZSET or INCR+EXPIRE) — they'll ask.
rateLimiter.js
class RateLimiter {
  constructor(limit, windowMs) {
    this.limit = limit; this.win = windowMs; this.hits = new Map();
  }
  allow(key) {
    const now = Date.now();
    const q = this.hits.get(key) ?? [];
    while (q.length && q[0] <= now - this.win) q.shift(); // expire old
    if (q.length >= this.limit) { this.hits.set(key, q); return false; }
    q.push(now); this.hits.set(key, q); return true;
  }
}

Complexity: amortized O(1) per call; O(keys × limit) memory. Common mistakes: fixed-window boundary burst (2×limit across the seam) — sliding window fixes it; unbounded memory for idle keys (add sweep/TTL). Follow-ups: Distributed version: ZADD score=now, ZREMRANGEBYSCORE old, ZCARD, EXPIRE — atomically via Lua. Token bucket vs sliding window tradeoffs. Per-tenant fairness vs per-IP.

Problem: Process at-least-once events without duplicate side effects; retries must return the original result.

Step-by-step

  • 1. Derive a stable idempotency key (client-provided or content hash).
  • 2. Atomically claim the key (SET NX EX / unique constraint) BEFORE side effects.
  • 3. Store the result for replay; on failure, release the claim so a retry can proceed.
idempotent.js
async function idempotentHandler(store, event) {
  const key = event.idempotencyKey ?? hash(event);

  // Atomic claim — SET NX EX in Redis, or unique row in Postgres
  const claimed = await store.setIfAbsent(key, 'processing', 86400);
  if (!claimed) return store.getResult(key); // duplicate → replay

  try {
    const result = await processEvent(event);
    await store.setResult(key, result);
    return result;
  } catch (err) {
    await store.clear(key);   // let a safe retry proceed
    throw err;
  }
}

Complexity: O(1) extra work per event; O(distinct keys) dedup storage. Common mistakes: check-then-act race; side effects before claim; never releasing a claim on failure (poison lockout). Follow-ups: What if the process dies between claim and result? (TTL + retry.) Dedup window sizing vs max retry interval. How Postgres unique constraints beat Redis for durable claims.

Problem: K async streams, each sorted by timestamp; emit one globally sorted stream without buffering everything.

Step-by-step

  • 1. Prime the head of every stream.
  • 2. Repeatedly yield the smallest head, refilling from its stream.
  • 3. Naive min-scan is O(K) per item — state that a binary heap makes it O(log K), and offer to swap it in.
mergeStreams.js
async function* mergeSorted(streams) { // each: async iterable of {ts,…}
  const heads = new Map();
  const iters = streams.map(s => s[Symbol.asyncIterator]());

  for (const it of iters) {
    const r = await it.next();
    if (!r.done) heads.set(it, r.value);
  }

  while (heads.size) {
    let minIt = null;
    for (const [it, v] of heads)
      if (minIt === null || v.ts < heads.get(minIt).ts) minIt = it;

    yield heads.get(minIt);
    const r = await minIt.next();
    r.done ? heads.delete(minIt) : heads.set(minIt, r.value);
  }
}

Complexity: O(N·K) time with linear scan → O(N·log K) with heap; O(K) memory — constant per input size, which is the point. Common mistakes: collecting all streams into memory first (defeats streaming); ignoring that async heads need awaits. Follow-ups: Late-arriving out-of-order events — add a watermark/allowed-lateness window. Dedup by (device, seq) during merge. Why this matters here: merging per-gateway streams into one ordered feed.

  • S3: hourly Parquet dumps from Kafka (tiered retention) for replay + analytics.
