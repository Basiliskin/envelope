Interactive Training Cards

Key concepts with real-world examples, best practices, and mini quizzes

🔹 Idempotency Medium

Concept: An operation that can be applied multiple times without changing the result beyond the initial application.

Real-world example: In a payment system, if a client retries a payment request due to a timeout, the server should process it only once and return the same response.

Best practices: Use idempotency keys in headers, store results in a cache/database, and return cached responses for retries.

✅ Do

  • Generate unique idempotency keys per request
  • Store results with TTL

❌ Don't

  • Rely on client-side generated keys without validation
  • Forget to handle key expiration

Common pitfalls: Race conditions on key lookup, not handling key collisions, caching too long.

What is the primary benefit of idempotency in a distributed system?

🔹 Circuit Breaker Medium

Concept: A pattern that prevents an application from repeatedly trying to execute an operation that's likely to fail, allowing it to recover gracefully.

Real-world example: When a downstream payment service is slow, the circuit breaker opens and returns a fallback response instead of timing out.

Best practices: Use three states (closed, open, half-open), configure thresholds for failure rate and timeouts, and implement monitoring.

✅ Do

  • Set appropriate thresholds based on SLAs
  • Log state changes for debugging

❌ Don't

  • Use default values without tuning
  • Ignore the half-open state

Common pitfalls: Thresholds too sensitive causing false positives, not resetting after recovery.

What state does a circuit breaker enter to test if the downstream service has recovered?

🔹 Eventual Consistency Hard

Concept: A consistency model used in distributed systems where updates are propagated asynchronously, and data may be temporarily inconsistent but will become consistent over time.

Real-world example: In a case management system, when a lawyer updates a case status, the client's view might lag by a few seconds due to asynchronous replication.

Best practices: Design for idempotency, use idempotent consumers, and implement reconciliation mechanisms.

✅ Do

  • Use event sourcing to track changes
  • Implement idempotent message processing

❌ Don't

  • Assume strong consistency without explicit design
  • Ignore conflict resolution

Common pitfalls: Not handling duplicate messages, missing reconciliation logic.

Which pattern is commonly used to handle eventual consistency?

Core concepts: Event loop, async/await, streams, modules (CommonJS/ESM), child processes, clustering.

Important APIs: http, fs, path, events, stream, child_process, cluster.

Common interview questions:

  • "How do you handle uncaught exceptions?"

Coding questions: "Write a function that reads a large file line by line and processes each line without loading the entire file into memory."

System design considerations: Clustering for multi-core, graceful shutdown, health checks, observability.

Coding Interview Preparation

Likely problems with step-by-step solutions

📝 Problem: Rate Limiter

Question: Design a rate limiter that limits each user to 100 requests per minute. Implement it in Node.js/TypeScript.

Solution (step-by-step):

  • Use a sliding window counter stored in Redis.
  • Key: rate_limit:{userId} with a score of timestamp.
  • For each request, remove entries older than 60 seconds, count remaining, and if < 100, add the current timestamp.
import { Redis } from 'ioredis'; const redis = new Redis(); const WINDOW = 60; const LIMIT = 100; async function rateLimit(userId: string): Promise<boolean> { const key = `rate_limit:${userId}`; const now = Date.now(); const cutoff = now - WINDOW * 1000; // remove old entries await redis.zremrangebyscore(key, 0, cutoff); const count = await redis.zcard(key); if (count < LIMIT) { await redis.zadd(key, now, `${now}-${Math.random()}`); await redis.expire(key, WINDOW); return true; } return false; }

Complexity: O(log N) for each operation (Redis sorted set).

Common mistakes: Forgetting to expire keys, race conditions in distributed environments.

Follow-up: How would you scale this across multiple servers? (Use a distributed cache like Redis.)

📝 Problem: Design a Task Queue

Question: Design a task queue system that processes jobs asynchronously with retries and error handling.

Solution (step-by-step):

  • Use a message broker like SQS or Redis.
  • Producer pushes jobs with a unique ID and payload.
  • Consumer polls for jobs, processes them, and deletes on success.
  • On failure, push to a dead-letter queue after max retries.
import { SQS } from 'aws-sdk'; const sqs = new SQS(); const QUEUE_URL = '...'; const DLQ_URL = '...'; const MAX_RETRIES = 3; async function processJob(job: any): Promise<void> { try { await doWork(job); await sqs.deleteMessage({ QueueUrl: QUEUE_URL, ReceiptHandle: job.ReceiptHandle }).promise(); } catch (err) { const retryCount = job.Attributes?.ApproximateReceiveCount || 1; if (retryCount >= MAX_RETRIES) { await sqs.sendMessage({ QueueUrl: DLQ_URL, MessageBody: JSON.stringify(job) }).promise(); } else { // visibility timeout will trigger retry } } }

Complexity: O(1) per job with SQS.

Common mistakes: Not handling duplicate messages, not setting visibility timeout correctly.

Follow-up: How do you ensure exactly-once processing? (Design for idempotency.)

System Design

Walkthrough: Case Management System for Flare

📋 Requirements Gathering

Functional:

  • Attorneys can create, update, and view cases
  • Clients can track case status and view documents
  • Documents can be uploaded and shared
  • Real-time notifications for status changes

Non-functional:

  • Scalable to 10k+ concurrent users
  • 99.9% availability
  • Data encryption at rest and in transit
  • Audit logging for compliance

🏗️ High-Level Architecture

  • Client: Web/mobile apps talking to API Gateway
  • API Gateway: Routes requests to appropriate services
  • GraphQL Gateway: Aggregates data from microservices
  • Services: Case Service, User Service, Document Service, Notification Service
  • Databases: Postgres (transactional), Elasticsearch (search), Redis (cache)
  • Message Queue: SQS for async tasks (notifications, document processing)
  • Storage: S3 for documents
  • Observability: CloudWatch, X-Ray, structured logging

🧩 Component Breakdown

Case Service: CRUD operations on cases, status transitions, event publishing.

User Service: User management, authentication, authorization (RBAC).

Document Service: Upload, download, versioning, and sharing of documents.

Notification Service: Sends email/SMS/push notifications for status changes.

🗄️ Database Design

-- Postgres schema CREATE TABLE users ( id UUID PRIMARY KEY, email TEXT UNIQUE NOT NULL, name TEXT NOT NULL, role TEXT NOT NULL, created_at TIMESTAMP DEFAULT NOW() ); CREATE TABLE cases ( id UUID PRIMARY KEY, title TEXT NOT NULL, status TEXT NOT NULL, client_id UUID REFERENCES users(id), attorney_id UUID REFERENCES users(id), created_at TIMESTAMP DEFAULT NOW(), updated_at TIMESTAMP DEFAULT NOW() ); CREATE TABLE documents ( id UUID PRIMARY KEY, case_id UUID REFERENCES cases(id), name TEXT NOT NULL, s3_key TEXT NOT NULL, uploaded_by UUID REFERENCES users(id), created_at TIMESTAMP DEFAULT NOW() ); CREATE INDEX idx_cases_client ON cases(client_id); CREATE INDEX idx_cases_attorney ON cases(attorney_id); CREATE INDEX idx_documents_case ON documents(case_id);

📈 Scaling

  • Horizontal scaling: Run multiple instances of each service behind a load balancer.
  • Database: Read replicas for read-heavy queries, partitioning by tenant (law firm).
  • Caching: Redis for frequently accessed case data, session storage.
  • CDN: Serve static assets and documents via CloudFront.

⚡ Caching Strategy

  • Cache-aside: Check cache first, then DB on miss.
  • TTL: 5 minutes for case data, 1 hour for user profiles.
  • Invalidation: On case update, invalidate cache for that case.
  • Distributed cache: Redis Cluster for high availability.

📨 Messaging

  • SQS: For async tasks — document processing, email notifications.
  • SNS: For fan-out notifications to multiple subscribers.
  • EventBridge: For event-driven workflows (e.g., case status change → notify client).

📊 Monitoring

  • Metrics: Request rate, error rate, latency (p50, p95, p99).
  • Logging: Structured JSON logs with correlation IDs.
  • Alerts: On error rate > 1%, latency p95 > 500ms.
  • Dashboards: Grafana or CloudWatch dashboards.

🔒 Security

  • Authentication: OAuth2 with JWT tokens.
  • Authorization: RBAC — attorneys can only access their cases.
  • Encryption: TLS in transit, AES-256 at rest (S3, RDS).
  • Audit logs: All access and changes logged for compliance.

⚖️ Tradeoffs

  • Microservices vs Monolith: Microservices for independent scaling and team ownership, but adds complexity.
  • GraphQL vs REST: GraphQL gives clients flexibility but requires careful query optimization.
  • Postgres vs NoSQL: Postgres for strong consistency, NoSQL for high-throughput event storage.
  • Serverless vs Containers: Serverless for low-traffic services, containers for predictable workloads.
