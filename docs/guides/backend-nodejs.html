TIER 1 · 01

The Event Loop

Node is single-threaded but not single-file: your code, timers, I/O callbacks and microtasks all wait in different lines. Senior answers are about which queue runs when — and what starves what.

🎯 WHAT THE INTERVIEWER IS LISTENING FOR "The call stack runs sync code to completion. nextTick drains before microtasks; both drain after every task and between every phase. Timers are a phase, not a queue — setTimeout(0) means 'at least 0ms, when the timers phase next runs'."

Phases — click each one

→ → → → ↺
Executes expired setTimeout/setInterval callbacks. Node checks expiry time when the phase runs — timers are never early, can be late.

Crucial addendum: process.nextTick() and the microtask queue (Promise.then, queueMicrotask) drain between every phase and after every callback — they effectively cut in line, which is exactly why abusing them can starve I/O.

LIVE — A BLOCKING MICROTASK DELAYS TIMERS runs for real in this tab

A microtask that blocks the thread delays everything behind it, including timers that are already due. Run it and watch the elapsed times:

✗ DON'T — starve the loop
sync-heavy.js
// JSON.parse of a 40MB payload inside a request handler
app.post('/import', (req, res) => {
  const data = JSON.parse(req.body.huge); // blocks for ~800ms
  // EVERY other request waits. Timers fire late. Healthchecks fail.
});
One blocked loop = the whole process frozen. CPU-bound work belongs in a worker thread, a separate service, or streamed incrementally.
✓ DO — keep callbacks short, offload the heavy part
offload.js
import { Worker } from 'node:worker_threads';
app.post('/import', (req, res) => {
  const w = new Worker('./parse-worker.js');
  w.postMessage(req.body.huge);
  w.on('message', (data) => res.json({ ok: true, rows: data.length }));
});
The event loop stays free to serve everyone else; the CPU work happens on a real parallel thread.
  • setTimeout(fn, 0) inside an I/O callback vs setImmediate(fn): inside I/O callbacks, setImmediate is guaranteed first (check phase follows poll). In the main module, their order is technically indeterminate — saying that out loud is a senior signal.
  • process.nextTick fires before any other microtask; prefer queueMicrotask unless you truly need to go first (recursive nextTick can starve I/O).
TIER 1 · 02

Promises & async/await

Combinators are vocabulary: all fails fast, race takes the first settled, any takes the first fulfilled, allSettled never rejects. The senior layer is knowing what happens to the losers of each race (they keep running) and how errors propagate.

LAB — COMBINATOR PLAYGROUND real promises, real timing

Fan-in with fail-fast. Count down completions; first rejection settles everything.

promise-all.ts
function promiseAll<T>(ps: Iterable<T | Promise<T>>): Promise<T[]> {
  const list = [...ps];
  return new Promise((resolve, reject) => {
    const out = new Array(list.length);
    let left = list.length;
    if (left === 0) return resolve(out);
    list.forEach((p, i) =>
      Promise.resolve(p).then(
        (v) => { out[i] = v; if (--left === 0) resolve(out); }, // preserve ORDER, not finish order
        reject,                                                 // first rejection wins
      ));
  });
}

First settlement (fulfil OR reject) wins. Classic use: racing work against a timeout.

promise-race.ts
function promiseRace<T>(ps: Promise<T>[]): Promise<T> {
  return new Promise((resolve, reject) =>
    ps.forEach((p) => Promise.resolve(p).then(resolve, reject)));
}
// the timeout pattern you'll be asked about:
const withTimeout = <T>(p: Promise<T>, ms: number) =>
  Promise.race([p, new Promise<never>((_, rej) =>
    setTimeout(() => rej(new Error(`timeout ${ms}ms`)), ms))]);

First fulfilment wins; collect rejections; if all reject, throw AggregateError.

promise-any.ts
function promiseAny<T>(ps: Promise<T>[]): Promise<T> {
  return new Promise((resolve, reject) => {
    const errs: unknown[] = new Array(ps.length);
    let left = ps.length;
    if (left === 0) reject(new AggregateError([], 'no promises'));
    ps.forEach((p, i) => Promise.resolve(p).then(resolve, (e) => {
      errs[i] = e;
      if (--left === 0) reject(new AggregateError(errs, 'all rejected'));
    }));
  });
}

Wait for everything, reject nothing. Perfect for "do N things, report each outcome" (batch jobs, fan-out notifications).

promise-allsettled.ts
function promiseAllSettled<T>(ps: Promise<T>[]) {
  return Promise.all(ps.map((p) =>
    Promise.resolve(p).then(
      (value)  => ({ status: 'fulfilled' as const, value }),
      (reason) => ({ status: 'rejected'  as const, reason }),
    )));
}
✗ DON'T — await in series what can run in parallel
serial.ts
const user    = await fetchUser(id);     // 120ms
const orders  = await fetchOrders(id);   // +150ms
const balance = await fetchBalance(id);  // +90ms
// total ≈ 360ms — each call waited for the previous
Three independent network calls chained into one slow request. The event loop could have overlapped them.
✓ DO — fan out, join with Promise.all
parallel.ts
const [user, orders, balance] = await Promise.all([
  fetchUser(id), fetchOrders(id), fetchBalance(id),
]);
// total ≈ 150ms — bounded by the slowest call
Rule of thumb: await only what the next line genuinely depends on.
✗ DON'T — async inside forEach
foreach.ts
ids.forEach(async (id) => {
  await sendEmail(id); // forEach IGNORES the returned promises
});
console.log('all sent'); // lies — fires immediately
forEach swallows promises: no waiting, and rejections become unhandled.
✓ DO — for…of (sequential) or map + all (parallel)
loops.ts
for (const id of ids) await sendEmail(id);      // one at a time
await Promise.all(ids.map((id) => sendEmail(id))); // all at once (mind limits → §03)
Both actually await completion and propagate errors to your try/catch.

Cancellation — AbortController

abort.ts
// Node 18+ / browsers: timeouts built in
const res = await fetch(url, { signal: AbortSignal.timeout(3_000) });

// Manual: cancel a whole unit of work
const ac = new AbortController();
setTimeout(() => ac.abort('client disconnected'), 5_000);
await doWork({ signal: ac.signal }); // check signal.aborted between steps

// TS-friendly error narrowing
try { await fetch(url, { signal: ac.signal }); }
catch (e) {
  if (e instanceof DOMException && e.name === 'AbortError') return; // user choice, not a bug
  throw e;
}
🎯 INTERVIEW SIGNAL Mention that aborting doesn't kill running CPU work — cooperative cancellation means your code checks signal.aborted at safe points and unwinds resources.
TIER 1 · 03

Concurrency

Promise concurrency is interleaving, not parallelism: one thread still runs one statement at a time. That gives you free overlap of I/O — and free race conditions on shared state. CPU-bound work needs real threads (worker_threads).

LAB — CONCURRENCY LIMITER (mapLimit) watch the in-flight ceiling
press run — each bar is an async task; only limit ever run at once
map-limit.ts — build this from scratch once
async function mapLimit<T, R>(
  items: T[], limit: number, fn: (item: T, i: number) => Promise<R>,
): Promise<R[]> {
  const results: R[] = new Array(items.length);
  let next = 0;
  async function worker() {
    while (next < items.length) {
      const i = next++;               // claim BEFORE any await — no two workers grab the same index
      results[i] = await fn(items[i], i);
    }
  }
  await Promise.all(Array.from({ length: Math.min(limit, items.length) }, worker));
  return results;
}
✗ DON'T — unbounded fan-out
unbounded.ts
// 10k open sockets, EMFILE, rate-limit ban, DB connection pool exhausted
await Promise.all(users.map((u) => enrichFromApi(u)));
Parallelism without a ceiling is a DDoS on your own dependencies.
✓ DO — cap in-flight work
bounded.ts
await mapLimit(users, 20, enrichFromApi); // or p-limit / p-queue
Same shape as connection pools: the limit is chosen from the downstream's capacity, not your CPU.
✗ DON'T — read-modify-write on shared state
race-condition.ts
// two requests interleave at each await → lost update
const seat = await db.seat.find(id);   // both read: free
if (seat.free) {
  await db.seat.update(id, { free: false, userId }); // both write
}
Every await is a point where another task can slip in. Single-threaded ≠ safe.
✓ DO — make the check-and-set atomic
atomic.ts
// conditional UPDATE: the database serializes it
const { count } = await db.query(
  `UPDATE seats SET free = false, user_id = $1
   WHERE id = $2 AND free = true`, [userId, id]);
if (count === 0) throw new ConflictError('seat taken');
// same idea: SELECT ... FOR UPDATE, Redis SETNX, unique constraints
Push atomicity into a layer that actually serializes: DB row lock, Redis, or a unique index.

CPU-bound vs I/O-bound

worker-pool.ts
// parent
import { Worker } from 'node:worker_threads';
function hash(password: string): Promise<string> {
  return new Promise((resolve, reject) => {
    const w = new Worker('./hash.worker.js', { workerData: password });
    w.once('message', resolve);
    w.once('error', reject);
  });
}
// hash.worker.js
import { parentPort, workerData } from 'node:worker_threads';
import { scryptSync } from 'node:crypto';
parentPort.postMessage(scryptSync(workerData, 'salt', 64).toString('hex'));

Decision rule: waiting (network, disk) → async/await is perfect; computing (image resize, parsing, crypto) > a few ms → worker thread or separate service. async never makes CPU work faster — it just hides waits.

TIER 1 · 04

Streams & Backpressure

Streams process data in chunks so memory stays flat while throughput stays high. Backpressure is the protocol by which a slow consumer tells a fast producer to slow down — write() returns false, you wait for 'drain'. Ignoring it turns "large file upload" into "OOM at 3am".

LAB — BACKPRESSURE OR OOM producer 45/s vs consumer 12/s
0 / 100 chunks
💥 FATAL ERROR: Reached heap limit — buffer grew without bound. This is what happens when you ignore write()'s return value.

Try it: with backpressure on, the producer pauses at the yellow line and resumes after drain — throughput is capped but the process lives. Turn it off and watch the crash.

✗ DON'T — buffer the whole file
whole-file.ts
const data = await fs.readFile('4gb-video.mp4'); // RAM explodes
res.send(data);
// also wrong: pipe without error handling
src.pipe(dest); // a read error leaves dest half-written, unhandled 'error'
Memory ∝ file size. One big upload kills the process for every other user.
✓ DO — stream + pipeline()
pipeline.ts
import { pipeline } from 'node:stream/promises';
await pipeline(
  fs.createReadStream('4gb-video.mp4'),   // Readable
  zlib.createGzip(),                       // Transform
  res,                                     // Writable (HTTP)
); // errors propagate, all streams get destroyed, no leaks
Constant memory, automatic backpressure, single error path. pipeline > .pipe() — always.
manual-backpressure.ts — what pipeline does for you
readable.on('data', (chunk) => {
  const ok = writable.write(chunk);       // false = internal buffer is full
  if (!ok) {
    readable.pause();                     // stop pulling…
    writable.once('drain', () => readable.resume()); // …until consumer catches up
  }
});
s3-upload-stream.ts — streams + HTTP + S3
import { Upload } from '@aws-sdk/lib-storage';
import { PassThrough } from 'node:stream';

// pipe the HTTP request body straight to S3 — never hold it in memory
const bridge = new PassThrough();
const upload = new Upload({ client: s3, params: { Bucket, Key, Body: bridge } });
req.pipe(bridge);
req.on('error', () => bridge.destroy());  // client disconnects → abort upload
await upload.done();
🎯 INTERVIEW SIGNAL Name the default highWaterMark (16KB / 16 objects), explain objectMode, and say why pipeline cleans up on error while pipe doesn't.
TIER 1 · 05

Memory & Garbage Collection

Locals live on the stack (freed when functions return); objects live on the heap, reclaimed only when unreachable. A "memory leak" in JS is simply accidental reachability: something keeps pointing at data you think is gone. Buffers live off the V8 heap — track them via process.memoryUsage().

LAB — SIMULATED HEAP red = reachable (survives GC), striped = garbage
heapUsed ≈ 0MB
⚠ heap near --max-old-space-size → next major GC or allocation = OOM kill

GC only collects garbage. Click the leaks a few times, then sweep — the red part never goes away. That asymmetry is the entire diagnosis.

Spot the leak — click your answer on each card

A — module cache

const cache = new Map(); // module scope
app.get('/u/:id', (req, res) => {
  cache.set(req.params.id, await load(req.params.id));
});

LEAKS: unbounded Map keyed by user input — every unique id lives forever. Fix: LRU with max size + TTL (§09), or WeakMap when keys are objects.

B — listeners

emitter.on('data', handler);
// inside a per-request function,
// never emitter.off(...)

LEAKS: each request pins another handler (and its closure!) forever. Node even warns: MaxListenersExceededWarning is a gift — listen to it.

C — WeakMap

const meta = new WeakMap();
app.use((req, res, next) => {
  meta.set(req, { start: Date.now() });
  next();
});

SAFE: WeakMap keys are weakly held — when the request object dies, the entry becomes collectible. This is what WeakMap is for.

  • V8 GC in one breath: young generation (Scavenge, fast, minor) + old generation (Mark-Sweep / Mark-Compact, slower, major). Leaks = objects promoted to old space that never become unreachable.
  • Diagnosis: node --inspect app.js → Chrome DevTools → Memory → take heap snapshots over time and diff (objects growing between snapshots = suspects). Server-side: process.memoryUsage() logged to your metrics; --max-old-space-size to make OOMs deterministic instead of mysterious.
  • Classic leak roster: global Maps/arrays, timers never cleared, listeners never removed, closures over big scopes, cached Promises that never settle, accidental globals (x = 1 without declaration in sloppy mode).
TIER 1 · 06

Error Handling

The senior distinction: operational errors (expected failures: 404, timeout, validation, downstream 503 — handle and recover) vs programmer errors (bugs: TypeError, undefined dereference — the process is in an unknown state; log, crash, let the orchestrator restart).

✗ DON'T — swallow or half-handle
swallow.ts
try { await charge(card); }
catch (e) { /* TODO */ }        // silent failure — order "succeeds" unpaid

try { await save(data); }
catch (e) { logger.error(e); }   // logged AND lost — caller thinks it worked
A catch block must make a decision: recover, transform, or rethrow. "Log and continue" is usually neither.
✓ DO — typed errors, decide at the boundary
errors.ts
class AppError extends Error {
  constructor(
    message: string,
    readonly statusCode: number,
    readonly isOperational = true,
  ) { super(message); }
}
try { await charge(card); }
catch (e) {
  if (e instanceof PaymentDeclinedError)
    throw new AppError('Card declined', 402); // translate for the caller
  throw e;                                    // unknown → propagate unchanged
}
In NestJS this lands in an Exception Filter; the point is the same: one place maps errors to responses, everything else just throws honestly.

Predict what happens — then reveal

a.ts
try {
  setTimeout(() => { throw new Error('boom'); }, 10);
} catch (e) { console.log('caught!'); }
Nothing gets caught — uncaughtException. try/catch only sees errors thrown synchronously within its own execution; the callback runs later, outside the try. Inside callbacks you need the callback's own try/catch (or async/await, which restores this).
b.ts
async function f() { throw new Error('x'); }
f();
console.log('after');
after prints. An async function throwing returns a rejected promise — it never throws synchronously. Since nobody awaits f(), Node 15+ terminates the process with an unhandled rejection (right after the tick).
c.ts
Promise.reject(new Error('x'))
  .catch((e) => { throw e; });
No — throwing inside .catch produces a new rejected promise (the one returned by catch). If nothing handles that, it's unhandled again. A catch handler only "handles" an error if it doesn't rethrow/reject.
shutdown.ts — graceful shutdown, the interview classic
process.on('unhandledRejection', (reason) => {
  logger.fatal({ err: reason }, 'unhandled rejection');
  shutdown(1);                    // Node ≥15 crashes anyway — be explicit
});

let shuttingDown = false;
async function shutdown(code: number) {
  if (shuttingDown) return; shuttingDown = true;
  server.close();                          // 1) stop accepting NEW connections
  await Promise.race([
    drainInFlightRequests(),               // 2) let current work finish
    sleep(10_000),                         // 3) …but never forever
  ]);
  await db.$disconnect();                  // 4) release resources
  process.exit(code);
}
process.on('SIGTERM', () => shutdown(0));  // k8s sends SIGTERM, then SIGKILL after grace period
🎯 INTERVIEW SIGNAL Explain why we exit on programmer errors (unknown state can't be reasoned about), why SIGTERM handlers must have a force-exit timer, and why "just restart the pod" is a strategy — not an accident.

Idempotency — click a method

Why it matters: only idempotent operations are safe to retry blindly. A POST that charges a card needs an Idempotency-Key header stored server-side, so retries return the original result instead of charging twice.

LAB — RETRY WITH EXPONENTIAL BACKOFF + JITTER

delay = min(base × 2ⁿ, cap) × jitter. Jitter is not decoration — synchronized retries from 1000 clients without it create a thundering herd that re-crashes the service you're trying to save.

✗ DON'T — requests that never end
no-timeout.ts
const res = await fetch(url);
// if the server accepts the connection and then goes silent,
// this promise hangs FOREVER. One slow dependency →
// all your sockets and workers pile up behind it.
Every outbound call needs a deadline. Cascading failure starts exactly here.
✓ DO — timeouts everywhere, budgets end-to-end
timeouts.ts
const res = await fetch(url, { signal: AbortSignal.timeout(2_500) });
// budget thinking: if the client gives me 3s and I need 2 retries,
// each attempt gets <1.5s. Timeouts must SHRINK down the call chain.
Retry only retriable failures (5xx, timeouts, 429 — respect Retry-After), never 4xx, and never non-idempotent writes without a key.
LAB — RATE LIMITER (TOKEN BUCKET) the thing that returns those 429s
200 OK: 0 · 429: 0

Each request spends a token; tokens refill over time. Burst above capacity and the excess gets 429. Variants you should name: token bucket (this), leaky bucket (constant outflow), sliding window counters (Redis-friendly).

LAB — LRU CACHE (capacity-limited, recency-ordered)
lru.ts — the 10-line implementation they ask for
class LRU<K, V> {
  #m = new Map<K, V>();              // Map preserves insertion order
  constructor(private cap: number) {}
  get(k: K): V | undefined {
    if (!this.#m.has(k)) return undefined;
    const v = this.#m.get(k)!;
    this.#m.delete(k); this.#m.set(k, v);  // touch → move to newest
    return v;
  }
  set(k: K, v: V) {
    if (this.#m.has(k)) this.#m.delete(k);
    else if (this.#m.size >= this.cap)
      this.#m.delete(this.#m.keys().next().value!); // evict OLDEST
    this.#m.set(k, v);
  }
}
✗ DON'T — the three classic cache bugs
cache-bugs.ts
// 1) no TTL, no size cap → stale forever + memory leak (§05)
cache.set('cfg', config);

// 2) caching a live object → mutations leak between callers
const u = cache.get(id); u.name = 'hacked'; // every reader sees it

// 3) hot key expires → 5,000 requests all hit DB at once (stampede)
All three are real outages with post-mortems you could find.
✓ DO — TTL + jitter, immutable payloads, single-flight
cache-good.ts
cache.set('cfg', config, ttl(60_000 + jitter(10_000))); // spread expiry
cache.set(id, structuredClone(user));                    // or freeze it
// stampede guard: only ONE caller rebuilds, others await the same promise
const inflight = new Map<string, Promise<User>>();
async function getUser(id: string) {
  if (!inflight.has(id))
    inflight.set(id, load(id).finally(() => inflight.delete(id)));
  return inflight.get(id)!;
}
In Redis terms: maxmemory-policy allkeys-lru, SET key val EX ttl NX for locks.

async function consume(msg: OrderEvent) {
  // unique index on (message_id) makes this atomic across worker instances
  const inserted = await db.query(
    `INSERT INTO processed_events (message_id, at) VALUES ($1, now())
     ON CONFLICT DO NOTHING`, [msg.id]);

TIER 3 · 11

Closures

A function carries its birth environment with it: variables from the enclosing scope stay alive as long as the function is reachable — even after that scope has returned. That's encapsulation, that's React hooks, and that's half your memory leaks.

LAB — WATCH count SURVIVE
function counter() {
  let count = 0;                 // NOT global, NOT on the stack frame
  return () => ++count;          // the arrow function closes over `count`
}
const inc = counter();           // counter() returned… but count didn't die
[[Scopes]] of inc → { count: 0, …global }

The scope object lives on the heap, referenced by the returned function. No other code can touch count — this is the closest thing JS has to a private field, and exactly why an accidentally long-lived closure pins memory (§05).

the-loop-question.ts — asked constantly
for (var i = 0; i < 3; i++) setTimeout(() => console.log(i)); // ?
for (let j = 0; j < 3; j++) setTimeout(() => console.log(j)); // ?
3 3 3 then 0 1 2. var is function-scoped: all three callbacks close over the same i, which is 3 by the time they run. let creates a fresh binding per iteration, so each callback captures its own j.

The Prototype Chain

Property lookup is a walk: own properties → [[Prototype]] → its prototype → … → null. class/extends are syntax over exactly this. instanceof just walks the chain asking "do I hit X.prototype?"

dog→ Dog.prototype→ Object.prototype→ null
Own properties only: { name: 'Rex' }. bark() is NOT here — lookup walks up until it finds it.
✗ DON'T
proto-bad.ts
obj.__proto__ = other;        // slow, non-standard, mutates the chain live
Object.prototype.hi = fn;     // monkey-patching poisons EVERY object
if (obj.hasOwnProperty('x'))  // breaks if obj = Object.create(null)
Prototype mutation defeats engine optimizations and leaks behavior into unrelated code.
✓ DO
proto-good.ts
const clean = Object.create(null);         // no prototype at all — safe dict
Object.getPrototypeOf(obj);                // read the chain properly
Object.hasOwn(obj, 'x');                   // null-safe own-property check
class Dog extends Animal {}                // the chain, with guard rails
Read the chain, never rewrite it; prefer classes and composition.
TIER 3 · 13

this

Five rules, checked in this order: new binding → explicit (call/apply/bind) → implicit (obj.method()) → lexical (arrows capture the surrounding this) → default (undefined in strict mode). Detaching a method from its object is the #1 real-world bug here.

✗ DON'T — pass methods as bare callbacks
this-bad.ts
class Timer {
  seconds = 0;
  tick() { this.seconds++; }
}
const t = new Timer();
setInterval(t.tick, 1000);   // this === undefined (strict) → TypeError
The reference t.tick is just a function; the t. context evaporates the moment you hand it away.
✓ DO — bind at the boundary
this-good.ts
setInterval(() => t.tick(), 1000);   // arrow wraps the call site
setInterval(t.tick.bind(t), 1000);   // or pin it explicitly
// React era equivalent: class fields  tick = () => { this.seconds++; }
If you can state which of the five rules applies and why, this topic is done.
TIER 3 · 14

Equality & Coercion

=== compares without converting. == converts then compares (numbers win over strings, booleans become numbers, null only equals undefined). Object.is is the strictest: NaN equals NaN, and +0 ≠ −0. Senior stance: always ===, except the one blessed idiom x == null (catches null and undefined).

TypeScript, Advanced

The through-line: model states as unions, behavior as functions over them. Discriminated unions make impossible states unrepresentable; generics keep pipelines honest; narrowing turns runtime checks into compile-time guarantees.

result.ts — the pattern from your brief, fully wired
type Result<T> =
  | { success: true;  data: T }
  | { success: false; error: Error };

function handle(r: Result<User>) {
  if (!r.success) {
    r.error;            // : Error — the union NARROWED via the literal field
    throw r.error;
  }
  r.data;               // : User — no casts, no `!`
}

// exhaustiveness: if someone adds a third variant, this stops compiling
function assertNever(x: never): never {
  throw new Error('unhandled variant');
}

TIER ∞ · 18

Concurrency at System Scale

One client → one API → four services. Any arrow can fail, time out, or deliver twice. Your job is to design so that partial failure leaves the system consistent, recoverable, and honest — not "mostly fine".

topology — the interview whiteboard
                ┌─── Payment Service
Client → API → Order Service
                ├─── Inventory Service
                └─── Notification Service

Question: Inventory reserved ✓ … Payment declined ✗
Now what? You owe the system an ANSWER for this moment.
LAB — SAGA ORCHESTRATOR pick a failure, run the order

    Saga

    A chain of local transactions, each with a compensating action. Orchestration (one coordinator — easier to reason about) vs choreography (services react to events — looser coupling, harder to see the whole flow).

    Outbox pattern

    Write the domain change AND the event into the same DB transaction; a relay (poller / CDC / Debezium) publishes the event afterwards. Kills the "saved but never published" dual-write bug.

    Idempotency everywhere

    Client → API: Idempotency-Key header. Queue consumers: processed-message table. Retries become harmless replays instead of double charges.

    Eventual consistency

    Accept that replicas/services disagree for a while; design UX and invariants around "converges soon", not "always in sync".

    Distributed locks

    Redis SETNX + TTL for coarse coordination. Know the caveat: locks expire while work continues → fencing tokens or DB-level guarantees for correctness-critical paths.

    Timeouts, budgets & DLQ

    Every remote call: deadline. Every retry: cap + backoff. Every unprocessable message: dead-letter queue + alert — never silent drop, never infinite retry.

    outbox.ts
    await db.transaction(async (tx) => {
  await tx.orders.update(id, { status: 'PAID' });            // domain change
  await tx.outbox.insert({                                    // event, SAME transaction
    topic: 'orders', type: 'OrderPaid', payload: { id },
  });
});
// separate relay process: SELECT … FOR UPDATE SKIP LOCKED → publish → DELETE
    LAB — CIRCUIT BREAKER 3 fails in the last 5 calls → OPEN for 4s
    CLOSED

    CLOSED → traffic flows. OPEN → requests fail instantly without touching the sick service (that fast-fail is the whole point: it stops pile-ups). HALF-OPEN after the cooldown lets one probe through. Flip failure rate to 0% and watch recovery.
