    🚩 Over-engineering radar

    Before adding any component, answer these three honestly:

    1. What specific problem does it solve?If you cannot name a current, measurable pain point — wait. "We might need it someday" is not a problem.
    2. What does it actually cost?Operational burden, added latency, consistency headaches, debugging complexity, and team learning curve. Every component has a tax.
    3. What breaks if you DON'T add it?If the honest answer is "nothing today, maybe in 6 months," it is a luxury, not a need. Solve tomorrow's problems tomorrow.

    🎤 The 6-step interview playbook

    Use this exact order in the room. It keeps you from jumping to tools too fast and shows structured thinking.

    1. Clarify requirements first. Separate functional (what it does) from non-functional (how fast, how reliable, how much data). Always ask about scale: daily active users, peak QPS, data volume, read/write ratio, latency expectations, and geographic distribution. Write these numbers down — they justify every decision later.
    2. Estimate with back-of-envelope math. Calculate storage per year, requests per second, cache memory needed, and bandwidth. Round aggressively (2.5M seconds/month, 1KB per request). Interviewers care about your reasoning, not calculator precision. Numbers turn vague designs into justified architectures.
    3. Draw the high-level design first. Client → Load Balancer → API Layer → Services → Database, with cache and queue where needed. Draw the diagram before deep-diving into any single component. This shows you can see the forest before examining trees.
    4. Define data model & APIs. Sketch table schemas (or document shapes) and define 2–3 critical endpoint contracts. Explicitly justify your SQL vs NoSQL choice with trade-offs. Show you understand access patterns drive schema design, not the other way around.
    5. Scale the actual bottlenecks. For reads: indexes, cache, read replicas. For writes: async queues, batching, connection pooling. Only as a last resort: sharding. Always tackle the cheapest, simplest optimizations before the expensive, complex ones. Measure, then optimize.
    6. Discuss reliability & operations. Walk through failure modes: what happens when the database goes down? The cache? A third-party API? Cover idempotency, dead-letter queues, monitoring, graceful degradation, and deployment strategy. End by naming the trade-offs you consciously accept — this shows maturity.
    💬 Trade-offs beat tools. Always say what you give up when you pick something. "I chose X because Y, which means we lose Z — and we accept that because…"
    🧱 Start boring. Monolith, one SQL database, one cache, one queue. Scale only when forced by real metrics, not hypothetical future load.
    🏭 Name-drop real systems. "Like Twitter's fan-out problem" or "like Stripe's idempotency keys" shows you understand production reality, not just theory.
    🙋 Call out red flags yourself. "I would NOT shard here because the data fits on one node and sharding adds operational pain" scores more points than pretending complexity is free.
