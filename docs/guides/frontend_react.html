/ 01

React fundamentals

API — не главное. Главное — уметь ответить на вопрос «почему». Сначала — как устроен компонент и state, потом переверни карточку и ответь вслух.
component.tsx — функция, а не шаблон
function Welcome({ user }) {
  return <h1>Привет, {user.name}!</h1>;
}
// props — входные данные; ребёнок не может их менять
// на каждый render функция вызывается ЗАНОВО

Компонент — это функция. JSX — синтаксический сахар над React.createElement(): никакой «магии шаблонов» внутри нет.

state.tsx — состояние живёт вне компонента
function Counter() {
  const [count, setCount] = useState(0);
  return (
    <button onClick={() => setCount(count + 1)}>
      {count}
    </button>
  );
}

Значение count хранится не в переменной функции, а в fiber-узле. setCount лишь просит React перерисовать компонент.

UI = f(state)

Рендер — это вызов функции-компонента; React сам решает, когда и зачем перезапускать её. Отсюда растут все «почему» этого гайда: keys, memo, batching и порядок хуков.

клик по карточке — flip. Задача: ответить быстрее, чем за 20 секунд

/ 02

Do / Don't

Короткие «senior habits»: в каждой паре — плохой код, почему он плохой, и хороший код с тем же результатом.
✗ DON'T — key={index}
dont-index.tsx
{items.map((it, i) =>
  <Row key={i} item={it} />)} // позиция, а не личность
key — это идентичность для reconciliation. При reorder / insert / delete React путает «какой это элемент»: state и анимации переезжают на чужие строки.
✓ DO — стабильный id
do-id.tsx
{items.map((it) =>
  <Row key={it.id} item={it} />)} // идентичность элемента
Стабильный id задаёт идентичность, которая переживает сортировку и вставки. Генерируй id при создании объекта, а не по позиции в массиве.
✗ DON'T — синхронизировать state через useEffect
dont-sync.tsx
useEffect(() => {
  setFiltered(list.filter(...));
}, [list]);
// лишний render: сначала НЕ-отфильтрованный, потом отфильтрованный
«Set state in effect» почти всегда значит: значение нужно было вычислить при render, а не хранить. Это добавляет цикл render → effect → setState → render.
✓ DO — вычислять производные во время render
do-derive.tsx
const filtered = list.filter(...);
// каждый render пересчитывается — дешевле и предсказуемее
// если операция дорогая — оберни в useMemo
Производные значения считаются по ходу render: один рендер вместо двух, никаких гонок и «замороженного» state.
✗ DON'T — поднимать весь state наверх «на всякий случай»
dont-lift-all.tsx
const [query, setQuery] = useState(""); // на уровне App
// каждый ввод символа → re-render ВСЕГО поддерева
Чем выше живёт state, тем больше дерева перерисовывается при каждом изменении. «А вдруг пригодится» — не причина поднимать.
✓ DO — держать state как можно ниже
do-colocate.tsx
function SearchBox() {
  const [query, setQuery] = useState(""); // локально
  return <input value={query} onChange={...} />;
}
State живёт рядом с потребителем. Поднимай только когда он реально нужен нескольким веткам дерева.
✗ DON'T — новый объект в props мемо-ребёнку
dont-inline.tsx
<Child data={{ name: "John" }} />
// каждый render родителя = новый reference → memo бесполезен
Объекты и функции пересоздаются на каждый render. Shallow compare в React.memo видит новый reference и рендерит ребёнка заново.
✓ DO — стабильные ссылки
do-stable.tsx
const data = useMemo(() => ({ name: "John" }), []);
const onClick = useCallback(handleClick, []);
<Child data={data} onClick={onClick} />
Стабильный reference позволяет memo реально пропускать re-render. Но мемоизируй по делу (после замера), а не из страха — про это секция Performance.

на интервью формулируй «я бы сделал так, потому что…», а не «вот так правильно» — trade-off и есть часть senior-ответа

Rendering & references

Самая частая область на Senior-собеседовании: render → reconciliation → commit, batching, Fiber и идентичность объектов в props.
inline-object.tsx — новый ref каждый render
function Parent() {
  const [tick, setTick] = useState(0);
  return <Child data={{ name: "John" }} />;
  // ↑ новый объект на КАЖДОМ render
}
data ref → obj #1
✗ идентичность меняется → memo бесполезен
usememo.tsx — стабильный ref
const data = useMemo(
  () => ({ name: "John" }),
  []
);
return <Child data={data} />;
data ref → obj #1 · stable
✓ React.memo(Child) пропускает re-render
renders: 1 Child слева re-renderнулся: 1 раз Child справа: 1 раз

/ 04

Hooks: stale closure

Классическая задача на реальное понимание React. Разбери баг и три фикса — запускай каждый вариант и смотри на консоль.
useEffect(() => {
  const handler = () => setCount(count + 1); // count захвачен с 1-го render!
  window.addEventListener("click", handler);
  return () => window.removeEventListener("click", handler);
}, []); // ← пустые deps: handler живёт вечно со старым count
Stale closure. handler захватил count=0 из первого render. deps=[] → переподписки нет → каждый клик считает 0+1.
const handler = () => setCount(prev => prev + 1);
// ↑ функциональный апдейт: closure не нужен,
// актуальное значение даёт сам React
Работает. prev всегда актуален. Лучший фикс для «инкрементов» — deps=[] остаются валидными.
useEffect(() => {
  const handler = () => setCount(count + 1);
  window.addEventListener("click", handler);
  return () => window.removeEventListener("click", handler);
}, [count]); // ← переподписка на каждое изменение count
Работает, но каждый render с новым count = removeEventListener + addEventListener. Для interval/listeners на горячих данных — churn. Иногда это ок, иногда нет.
const countRef = useRef(0);
useEffect(() => { countRef.current = count; }); // синхронизация

const handler = () => setCount(countRef.current + 1);
// ↑ ref всегда держит последнее значение, closure не устаревает
Работает. Паттерн «latest value ref»: подписка создаётся один раз, значение всегда свежее. Тот же механизм внутри многих библиотек.

на интервью сначала назови баг вслух, потом предложи все три фикса и скажи про trade-offs — это и есть senior-ответ

/ 05

Rules of Hooks: как React хранит данные

React не знает имена твоих хуков — только позицию вызова. Отсюда правила хуков и их «неожиданные» ошибки.
fiber-hooks.js — как устроено внутри
// у каждого fiber-узла React хранит односвязный список хуков.
// вызов хука привязан к ИНДЕКСУ в этом списке, а не к имени:
fiber.memoizedState → { type: useState, idx: 0 }
                  → { type: useEffect, idx: 1 }
                  → { type: useRef,    idx: 2 }
// ↑ никаких имён — только порядок вызовов

Значения state хранятся вне функции компонента, в fiber-узле. Функция на каждый render выполняется заново, а React «подставляет» сохранённые значения по позиции вызова.

rules.md — правила
1. Хуки — только на верхнем уровне
2. Никогда в условиях / циклах / вложенных функциях
3. Только из компонентов и custom hooks (use*)
// eslint-plugin-react-hooks ловит это статически

Это не «style guide», а инвариант runtime: сломанный порядок = сломанная связка «вызов ↔ сохранённое значение».

conditional-hook.tsx — сломано
function Bad({ open }) {
  if (open) { // ← хук под условием
    const [a] = useState(0);
  }
  const [b] = useState(1);
}
// open=true:  2 хука на рендере
// open=false: 1 хук → индексы разъехались
// → «Rendered more hooks than during the previous render»
Ошибка React. На втором рендере хуков меньше — React не может сопоставить сохранённые значения с вызовами и падает, чтобы не отдать тебе чужое состояние.
stable-order.tsx — правильно
function Good({ open }) {
  const [a] = useState(0); // вызываются всегда
  const [b] = useState(1);
  return open ? <Panel a={a} /> : null;
  // условие — внутри JSX, порядок хуков не меняется
}

Хуки вызываются безусловно, условия выносятся в JSX или в колбэки. Порядок вызовов всегда один и тот же.

ЧТО ЛОМАЕТСЯ БЕЗ ПОРЯДКА

state привязывается по индексу: хук под условием «сдвигает» все следующие — useMemo, useEffect, useRef начинают читать чужие значения. Даже без краша это тихие баги.

ПОЧЕМУ ТАК СДЕЛАНО

React не хранит словарь «имя → state» — экономия памяти и простая реализация. Цена — дисциплина вызова: React доверяет стабильности порядка.

вопрос-перевёртыш на интервью: «почему eslint-plugin-react-hooks — защита, а не рекомендация?» — потому что нарушение меняет поведение runtime, а не стиль

/ 06

Modern React: RSC & Concurrent

React 19 и Next.js App Router. Граница сериализации и неблокирующие обновления.

🖥 SERVER COMPONENTS

Выполняются на сервере. Нет доступа к useState, useEffect или браузерным API. Идеальны для data fetching и работы с БД. Пропсы, передаваемые в Client Components, должны быть сериализуемы (JSON).

💻 CLIENT COMPONENTS

Директива "use client". Это обычный React, который гидратируется в браузере. Здесь живут интерактивность, стейт и обработчики событий. Импорт серверного компонента в клиентский запрещён (только через children).

// SORT: RSC BOUNDARY

🖥 SERVER → RSC

💻 CLIENT → "use client"

Что требует гидратации, а что останется на сервере? 0/6
concurrent.tsx — useTransition
const [isPending, startTransition] = useTransition();

function handleSearch(q) {
  startTransition(() => {
    setSearchQuery(q); // тяжёлый фильтр не заблокирует ввод
  });
}

Concurrent Feature: Помечает обновление как «не срочное». React может прервать его, если пользователь продолжит печатать, сохраняя UI отзывчивым (INP).

concurrent.tsx — useDeferredValue
const [query, setQuery] = useState("");
const deferredQuery = useDeferredValue(query);

// deferredQuery обновится, когда main thread освободится
<HeavyList query={deferredQuery} />

В отличие от debounce, который ждёт, useDeferredValue позволяет показать устаревшее значение, пока новое вычисляется в фоне.

React + TypeScript

Generics, discriminated unions, narrowing, utility types. Эталонный паттерн — типизированный useFetch<T>.
useFetch.ts — generic hook
type FetchResult<T> = {
  data: T | undefined;
  loading: boolean;
  error: Error | null;
};

function useFetch<T>(url: string): FetchResult<T> { /* … */ }

// discriminated union — narrowing через status
type Query<T> =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: T }
  | { status: "error"; error: Error };

unknown vs any: unknown заставляет сузить тип перед использованием — any выключает проверку entirely

Q1Данные из fetch ещё не проверены. Какой тип?
unknown — безопасный верхний тип: компилятор заставит сделать narrowing (type guard / zod) до использования. any отключает проверки.
Q2Какая запись — корректный discriminated union для состояния запроса?
Вариант 2: поле status — дискриминант. TS сам сужает тип: в ветке success data существует, error — нет. Вариант 1 допускает data+error одновременно.
Q3Типизация ref для <input>:
useRef<HTMLInputElement>(null): ref создаётся пустым и React присваивает DOM-узел при commit. Также знай React.ComponentProps и React.ElementRef для проброса props.

Web Vitals & Security

Senior мыслит метриками (Core Web Vitals) и угрозами. Кликни на карточку, чтобы увидеть диагноз и фикс.
✗ DON'T — XSS via dangerouslySetInnerHTML
xss-bad.tsx
function Comment({ text }) {
  return <div dangerouslySetInnerHTML={{__html: text}} />;
}
Если `text` приходит от пользователя, он может внедрить `<script>` или `onerror` атрибут. React экранирует текст по умолчанию, но этот хук отключает защиту.
✓ DO — Sanitize or use Markdown
xss-good.tsx
import DOMPurify from 'dompurify';

function Comment({ text }) {
  const clean = DOMPurify.sanitize(text);
  return <div dangerouslySetInnerHTML={{__html: clean}} />;
}
Всегда санитайзь HTML на клиенте (или, что лучше, на сервере) перед рендером. Либо используй AST-парсеры для Markdown.

JWT: никогда не храни в localStorage (уязвимо к XSS). Используй HttpOnly Secure Cookies. CSRF защищай через SameSite=Strict и CSRF-токены.
